# Rust packages

Status: decided 2026-11-14 for jade 2.0.4, and built on branch `2.0.4`, tested on macOS
on Apple Silicon. The Linux link path is written and unit-tested against a fake file
system, but no program with a Rust package has been linked on Linux yet; CI will be the
first to. Joe decided that
Rust replaces Jade's C foreign function interface and agreed the points marked *agreed*
below. Every other decision here was made while building it; each says why, and the
list at the end names them for review.

## The problem

Until 2.0.3 a native package was a shared library the program opened with `dlopen` while
it ran. A Jade package built by v1 exported `jade_pkg_init`; a plain C library got one
from a C shim that `jade pkg install` generated and compiled with `cc`. Either way every
call traded 16-byte tagged `JadeVal`s, and nothing in the library said what a function
took or returned, so the types came from `jade.toml`: `[lib.<name>.symbols]` for a Jade
package, and for a C library a symbol table written in the shim's own type vocabulary,
which `jade pkg add --header` generated by running clang over the library's header.

That came to about 7,000 lines: `pkg/bindgen.rs` read headers, `pkg/cshim.rs` wrote the
shim, `typechecker/infer/native.rs` read the declarations, and `backend/native.rs` loaded
the library and marshalled every value. Most of it existed to recover facts C does not
keep: who frees a string, whether a pointer is an out-parameter, how wide an integer is,
whether `-1` means failure. `pkg/README.md` records the bugs each rule came from. Every
one of them was a binding that compiled, linked and ran, and did the wrong thing.

Rust keeps those facts in its types. A `String` result is owned by whoever receives it, a
`&[u8]` is borrowed for the call, `Result<T, E>` says how a call fails, and `u32` is 32
bits. So the bridge can be written from the function's own signature, by the Rust
compiler, and nothing has to be guessed.

## What a package looks like

A Rust package is a library crate that depends on `jade-rs` and marks what Jade may call:

```rust
use jade::export;

#[export]
pub struct Point {
    pub x: f64,
    pub y: f64,
}

#[export]
pub fn midpoint(a: Point, b: Point) -> Point {
    Point { x: (a.x + b.x) / 2.0, y: (a.y + b.y) / 2.0 }
}

#[export]
pub fn resize(img: &[u8], width: u32) -> Result<Vec<u8>, String> {
    // ...
}
```

A Jade project names it as a dependency:

```toml
[dependencies.imgtools]
path = "rust/imgtools"        # a directory holding a Cargo.toml
abi = "rust"
```

and calls it like any package:

```jade
use imgtools

let p = imgtools.midpoint(imgtools.Point { x: 0.0, y: 0.0 }, imgtools.Point { x: 2.0, y: 4.0 })
print(p.y)                                        // 2.0
let small = imgtools.resize(fs.read_bytes("a.png"), 64)
```

A C library is reached the same way, through a Rust crate that wraps it: an existing
`-sys` crate, which builds or finds the library and declares its functions, plus a few
lines of safe Rust that `#[export]` the calls Jade needs. `examples/ffi/rust_zlib/` wraps
zlib through `libz-sys` that way.

## Decisions

### 1. The boundary is `extern "C"`, written in Rust (*agreed*)

Rust has no stable ABI and lays out a plain struct however it likes, so the compiled Jade
program cannot call a Rust function directly. The boundary stays the C calling
convention, and Rust code writes that layer: for each exported function, a
`#[no_mangle] extern "C"` wrapper the macro generates. For each exported struct, the
macro generates a `#[repr(C)]` mirror, which the Rust compiler lays out by C's rules, the
same way `cc` laid out the structs in the shim.

### 2. Two crates: `jade-rs` and `jade-rs-macros`

*agreed:* a macro crate of ours gives `#[jade::export]`. A proc-macro crate can export
nothing but macros, and the bridge needs traits the generated code calls, so there are two
workspace members in one directory:

- `jade-rs/`, package `jade-rs`, whose library is named `jade`. It holds the C forms of
  each type, the traits that convert a Rust value to and from one, the compile-time
  builder for the description, and the runtime pieces every wrapper calls. It re-exports
  the macro, so a package depends on this crate alone and writes `#[jade::export]`.
- `jade-rs/macros/`, package `jade-rs-macros`, the proc macro.

The library is named `jade` so that `jade-rs = { ... }` in a package's `Cargo.toml`
gives `#[jade::export]` with no rename. The compiler's own library is also called `jade`;
the two are never built in one cargo invocation, because the workspace's default member
is the compiler and `jade-rs` is tested with `-p`, so their outputs never meet.

The generated code reaches the runtime through the path `::jade`. A package that renames
the dependency writes `#[jade::export(crate = "other_name")]`, as serde does.

### 3. What the macro generates

On `pub fn resize(img: &[u8], width: u32) -> Result<Vec<u8>, String>` in crate
`imgtools`:

```rust
#[unsafe(no_mangle)]
pub unsafe extern "C" fn __jade_imgtools_resize(
    a0: *const jade::__private::CVec<u8>,  // the C form of `bytes`
    a1: *const u32,
    out: *mut jade::__private::CVec<u8>,
    err: *mut jade::__private::CVec<u8>,
) -> i32 { /* lift, call inside catch_unwind, lower */ }

#[unsafe(no_mangle)]
pub unsafe extern "C" fn __jade_imgtools_resize__free(
    out: *mut jade::__private::CVec<u8>,
    err: *mut jade::__private::CVec<u8>,
) { /* drop what the call handed over */ }
```

`#[unsafe(no_mangle)]` is what edition 2024 requires, and Rust accepts it in every
edition from 1.82, so a package needs Rust 1.82 or later. The tokens the macro writes take
the package's edition, so they are written to compile under all of them.

plus a description record (decision 7). The status is 0 when the call returned, and 1
when it raised, with the message in `err`.

The symbol is `__jade_<crate>_<function>`, so a package's exported names are one flat
namespace, as Jade's are: `imgtools.resize` names one function. Two exported functions
of one name in a crate collide, and rustc names the duplicate symbol.

On a struct, the macro requires named fields, every one `pub`, and no generics or
lifetimes, and generates the mirror, the conversions both ways, and a record.

*Refused at compile time, each with the fix named:* generic functions and structs,
`impl Trait` in an argument or the result, `&mut` arguments ("the Jade program would not
see what the function changes; take the value and return the new one instead"), raw
pointers, `async fn`, `unsafe fn`, an `extern` function, a variadic, a parameter written
as a pattern, methods, a struct with a private field or no named fields, and any type
with no Jade form. The last is a trait bound, so the message comes from
`#[diagnostic::on_unimplemented]` on the traits and names the types that do cross.

A borrow cannot outlive the call. Every argument is lifted for one call, and a borrowed
result, such as `fn first(s: &str) -> &str`, is copied into its C form before the
arguments it may borrow from are let go, so it is accepted rather than refused.

### 4. The types that cross (*agreed*)

| Rust | Jade | C form |
|------|------|--------|
| `i64`, `isize` | `int` | `int64_t` |
| `f64` | `float` | `double` |
| `bool` | `bool` | `uint8_t`, 0 or 1 |
| `char` | `char` | `uint32_t`, a Unicode scalar |
| `u8` | `byte` | `uint8_t` |
| `i16`, `u16` | `short`, `ushort` | `int16_t`, `uint16_t` |
| `i32`, `u32` | `int32`, `uint32` | `int32_t`, `uint32_t` |
| `u64`, `usize` | `ulong` | `uint64_t` |
| `f32` | `float32` | `float` |
| `&str`, `String` | `str` | `{ ptr, len, cap }` |
| `&[u8]`, `Vec<u8>` | `bytes` | `{ ptr, len, cap }` |
| `Vec<T>`, `&[T]` | `[T]` | `{ ptr, len, cap }` of `T`'s C form |
| `Option<T>` | `T?` | `{ uint8_t some; T value }` |
| `#[export] struct` | a class with public fields | the `#[repr(C)]` mirror |
| `Result<T, E>`, as a result | `T`, raising `E`'s text | `T`'s |
| `()` | `nil` | none |

`isize` and `usize` are this decision's: Rust uses them for every length and index, so
leaving them out would refuse most real signatures. They are 64 bits on every platform
Jade runs on, so they map to `int` and `ulong`, as `i64` and `u64` do. `i8`, `i128` and
`u128` have no Jade type and are refused.

`Vec<u8>` is `bytes`, not `[byte]`, because that is what a Rust API means by it. A `&T`
argument for any other type that crosses is lifted into a value the wrapper owns and
lent to the function. An `Option` of an `Option` is refused, since Jade has one `nil`.
`Result` crosses only as the whole result; its error type must implement `Display`, and
the raise carries `e.to_string()`.

### 5. Every value crosses as a pointer

Every argument is passed as a pointer to its C form, the result comes back through an
`out` pointer, and the status is the return value. Two reasons. LLVM IR does not apply
the C calling convention to a struct passed by value; clang and rustc each lower that
themselves, per platform, and the backend would have to repeat the rules. And an 8- or
16-bit integer must be sign- or zero-extended by the caller on some platforms and by the
callee on others. A pointer is passed the same way everywhere, so the backend needs
neither rule.

### 6. Ownership: what Jade sends is lent, what Rust returns is Rust's to free

*Arguments are Jade's.* A string or bytes argument points at the Jade string's own bytes
for the call, with no copy; Rust borrows it as `&str` or copies it into a `String`, as
the signature says. An array, optional or struct argument is built in temporary memory
by the caller, from the Jade value, and freed after the call. Nothing Rust receives
outlives the call, so Rust never frees Jade memory.

*Results are Rust's.* The wrapper lowers the result into its C form, allocating with
Rust's allocator, and the program copies it into Jade values: a string becomes a Jade
string, an array a Jade array, a struct an object of its class. Then the program calls the
function's `__free` companion, which rebuilds the Rust values and drops them. So no
allocator crosses the boundary in either direction, and no rule depends on where a value
sits. This replaces the shim's ownership rules (`out_buffer`, `alloc_str`, `frees_with`,
the per-thread string buffer), which existed because C does not say who frees.

*Text from a package is tainted,* as it was before: a string, bytes or char a Rust
function returns carries trust 1, so a program cannot hand it to `sh.exec` unchecked.

### 7. The description travels inside the built library

*agreed:* the macro produces a description of each signature for the checker, "the
headers regenerated in a crate". Three ways were weighed:

- *Parsing the package's source with syn* at check time. A proc macro sees tokens, not
  types, so `type Result<T> = std::result::Result<T, MyError>` is a one-argument
  `Result` to it, and so is every alias, every item a macro generates, and every
  `#[cfg]`. A description read from source can say something the compiled code does not.
- *A file the macro writes.* A proc macro that writes files is not rerun when cargo
  considers a crate fresh, and two crates building at once would write it together.
- *Metadata embedded in the library, as UniFFI does,* which is the choice. Each exported
  item adds a static to a section of its own, `__DATA,__jade_meta` on macOS and
  `.jade_meta` on Linux, holding one record: the bytes `JADEMETA`, a little-endian
  `u32` length, and JSON. The JSON is built at compile time by `const fn`s from an
  associated constant on each type's trait, so `Vec<MyAlias>` is described as what rustc
  resolved it to. The compiler builds the program's crate, then reads every record out of
  the staticlib with the `object` crate.

The cost is that `jade check` builds the Rust crate, since that is the only place the
description can come from. Cargo keeps the build, so a second check with nothing changed
spends a fraction of a second asking cargo.

A struct's record also carries its C size and alignment and each field's offset, from
`size_of` and `offset_of!`. The compiler computes the same layout from the field types
and refuses a mismatch, naming the struct, rather than reading fields at offsets rustc
did not use.

A function record looks like this:

```json
{"v":1,"kind":"fn","crate":"imgtools","name":"resize","symbol":"__jade_imgtools_resize",
 "params":[{"name":"img","type":"bytes"},{"name":"width","type":"uint32"}],
 "ret":"bytes","raises":true}
```

The type strings are Jade's own spelling. `v` is the record format; a record of another
format is refused with a message naming the `jade-rs` version to use.

### 8. Reusing UniFFI's ideas, not UniFFI

Mozilla's UniFFI was read first, and this design takes four ideas from it: the `Lift`
and `Lower` traits, named for the two directions; a result trait that lets `Result<T, E>`
lower differently from `T`; a call status with an error buffer, with `catch_unwind`
around every call so a panic never unwinds into foreign frames; and metadata built by
`const fn`s and read out of the compiled library, a staticlib included.

It does not use the crate, for three reasons. UniFFI serializes every compound value
into a byte buffer in its own format, so the Jade backend would have to generate a
deserializer for each type, where reading a C struct is a few loads it already knows how
to emit. Its metadata is an internal binary format that changes between UniFFI versions,
which would tie the compiler to one of them. And it brings a scaffolding setup macro,
objects, enums, callback interfaces and async, none of which Jade needs to start, and
dependencies every package would compile.

### 9. Errors and panics

`Err(e)` raises `e.to_string()`. A panic is caught by `catch_unwind` and raises
`imgtools.resize panicked: <the panic's message>`. An argument Rust refuses, such as a
string that is not UTF-8, raises before the function runs. The program raises the same
kind of error a failing `std` call does, so `try` and `catch` treat a Rust package like
any other code, and an uncaught one prints `jade: <message>` and exits with status 1.

A struct literal of a Rust struct's class must give every field, since Rust gives none a
default. The per-file type pass cannot see a class from another file, so the
whole-program member check reports a missing field of one, where it used to reach MIR.

Rust's default panic hook prints to stderr before the panic is caught. The runtime
installs a hook once, on the first call, that stays quiet while an exported call is
running on that thread and passes every other panic to the hook that was there before, so
a panic the package catches itself, or one on a thread of its own, still prints.

The generated crate is built with `panic = "unwind"`, which only the root crate's profile
decides, so a package cannot turn a raise into an abort.

### 10. One generated crate and one staticlib per project (*agreed*, with one change)

*agreed:* one generated Rust crate depends on all of a program's Rust packages and is
built once by cargo as a single staticlib, which LLD links into the program. Two Rust
staticlibs would each carry Rust's standard library and collide at link time.

*The change:* the crate is generated per project, not per program. Its dependencies are
every `abi = "rust"` entry in the project's `jade.toml`, and every program in the project
links the same library. The linker takes from an archive only the members a program
references, so a program that calls one package carries only that package's code, and a
project with several programs builds its Rust once.

The crate lives at `~/.jade/rust/<hash of the project's path>/`, named
`jade_program_<hash>`, with an empty `[workspace]` table so it is never mistaken for a
member of a workspace around it. Its `lib.rs` is one `extern crate` line per package,
which makes rustc link each one. Every project builds into one target directory,
`~/.jade/rust/target`, so `syn` and `jade-rs` compile once per machine. The compiler runs

```sh
cargo rustc --release --lib --message-format=json-render-diagnostics \
      --manifest-path ~/.jade/rust/<hash>/Cargo.toml --target-dir ~/.jade/rust/target \
      -- --print=native-static-libs
```

and reads the staticlib's path from cargo's JSON and the system libraries it needs from
the `native-static-libs` note, which cargo prints again when the crate is already built.
Cargo prints a build that failed as rustc renders it, and the compiler passes that
through without cargo's progress lines. A first build prints a note, since fetching and
compiling the crates takes a while; a later one is silent. `cargo metadata --offline`
then says which crate each dependency is, since a package may name its library apart
from itself and a record carries the library's name.

### 11. Linking

On Linux the staticlib and the libraries the note names are added to LLD's command line,
each found as a shared object in the directories the C library came from. `libgcc_s`,
which Rust's unwinder needs, is present on every glibc system.

On macOS, `link.rs` normally writes a stub of `libSystem` listing exactly the symbols the
object imports, so no SDK is needed. A Rust staticlib imports from whatever its `-sys`
crates link, such as `-lz` or `-framework Security`, and which member imports what is
the linker's decision. So a program with a Rust package links against Apple's SDK, found
with `xcrun --show-sdk-path`. Cargo already needs the SDK: rustc links every build script
and proc macro with the system's `cc`. A program with no Rust package links as before.

The built program needs nothing beside it. The Rust code is inside it, and it imports
only system libraries.

### 12. Cargo comes from `PATH` for now

*agreed:* jade installs its own dependencies, fetching a pinned, checksummed build rather
than printing an install command, as `dovata/src/quantize/install.rs` does for llama.cpp.
A Rust toolchain is several hundred MB, and fetching one needs a decision about which
components and where they live, so this pass runs `cargo` from `CARGO` or `PATH`. A
missing cargo stops the build with a message saying the program uses a Rust package and
naming the step to take. Fetching a pinned toolchain is the first follow-up.

### 13. The manifest

```toml
[dependencies.imgtools]
path = "rust/imgtools"                 # or git = "...", with rev, tag or branch
abi = "rust"                           # or version = "1.2.0", from crates.io

[dependencies.zlib]
path = "rust/zlib_jade"
package = "zlib-jade"                  # the Rust package's name, when it is not the Jade one
abi = "rust"
```

The key is the name a Jade program writes, so it is an identifier; `package` names the
Rust package when that has a `-` or differs otherwise. A Rust dependency is not recorded
in `jade.lock`, and `jade pkg install` has nothing to fetch for it: cargo fetches at
build time and pins the versions in the generated crate's `Cargo.lock`.

`abi` takes `"source"` and `"rust"`, and must be written: there is no prebuilt kind left
to default to. `abi = "c"` and `abi = "jade"` are refused with a message pointing here.

`jade pkg add <name> --path <dir>` writes a Rust dependency when the directory holds a
`Cargo.toml`, and `--rust` marks a `--git` or `--version` source as one. It builds the
package on the spot, so it reports what the package exports and refuses one that does not
compile, taking its entry back out of `jade.toml`.

### 14. Naming in a program

`use imgtools` binds the package; `imgtools.resize(...)` calls a function, and
`imgtools.Point { x: 1.0, y: 2.0 }` builds a struct, whose class has the Rust field
names, every field public. `from imgtools use resize, Point` works as for any package. A
name the package does not export is refused when the program is checked, with the closest
exported name suggested, as before.

## What changes in the compiler

- `jade-rs/` and `jade-rs/macros/`: the two new crates.
- `compiler/src/rustpkg/`: new. Writes the generated crate, runs cargo, reads the records
  out of the staticlib, checks each struct's layout, and turns records into signatures and
  classes. `aot/imports.rs` asks it for a project's packages the first time a `use`
  names one.
- `project/`: `Abi` is `Source` or `Rust`; `DependencyEntry` gains `package`; the C
  tables and `[lib]` symbol tables are gone, as is a `.dylib` or `.so` in `[lib]`.
- `pkg/`: Rust dependencies are skipped by the lock; `jade pkg add` detects a crate.
- `typechecker/infer/native.rs`: a signature is always complete, read from the record's
  type strings, so the checker no longer infers what an undeclared native call returns.
  A call passes each argument through `accept`, so a number literal takes a sized
  parameter's type. `typechecker/infer/members.rs` reports a missing public field of a
  class from another file.
- `typechecker/tir.rs` loses `JadeType::Handle`, so `CACHE_FORMAT_VERSION` is 18.
- `mir/`: a `NativeCall` names its symbol; `NativeLib` and runtime loading are gone.
- `backend/native.rs`: rewritten. Builds each argument's C form, calls the symbol, reads
  the result's C form into Jade values, calls `__free`, and raises on status 1.
- `backend/link.rs`: links the staticlib and its system libraries.

## What is removed

`pkg/cshim.rs`, `pkg/bindgen.rs` and their tests; `[lib.<name>.symbols]` and
`[lib.<name>.structs]`; `[dependencies.<name>]` `symbols`, `structs`, `headers`,
`include_dirs` and `defines`; `abi = "c"` and `abi = "jade"`, with prebuilt libraries
fetched by `url` and their per-platform artifacts; `jade pkg add --header`, `--c-abi`,
`--include`, `--define` and `--only`, and `jade pkg bind`; loading with `dlopen`, the
`JadeVal` format, and copying `libs/` beside a built program; the `handle<T>` type; and
`scripts/ffi-gate.sh`'s glib run with its fixtures, replaced by a gate over a Rust crate.

Removing `abi = "jade"` goes past what Joe named, which was the C path. A Jade-ABI
package came only from v1's `jade build --lib`, and a `jade.toml` declaration was the only
way to give its functions types; with those declarations removed, and Rust the only native
path, nothing can produce or type one, so the loader went with them.

## Out of scope

- *Iterators.* An exported function returning a Rust iterator is where pipes will connect:
  a Rust `Iterator` becoming a Jade stream belongs to the pipe work Joe is designing. For
  now a function returns a `Vec`.
- *Opaque values,* such as a database connection Jade holds and Rust keeps the inside of.
  The sketch: `#[jade::export(opaque)]` on a struct crosses it as a handle owning a
  `Box`, whose release calls the type's drop, and methods take `&self`. Handles are gone
  until then.
- *Callbacks,* a Jade function passed as `&dyn Fn(...)`. The rule that carries over: a
  raise inside the callback must not unwind through Rust frames, so the trampoline
  records it and returns, and the call raises once Rust returns.
- *Dicts, JSON, enums, tuples, `impl` blocks and `async fn`.*
- *Cross-compiling.* The crate is built for the machine the compiler runs on.

## Follow-ups, in order

1. Fetch a pinned, checksummed Rust toolchain when no cargo is found, in `~/.jade/`,
   following `dovata/src/quantize/install.rs`.
2. Keep the generated crate's `Cargo.lock` with the project, so a fresh clone builds the
   same Rust dependency versions.
3. Opaque values and callbacks, as sketched above.
4. Publish `jade-rs` to crates.io. Until then a package outside this repo depends on it by
   git, at the tag of the compiler it targets.
5. Lend arrays of numbers without a copy: an `[int]` argument's elements are already
   `int64_t`s in a row.
6. Link a program with a Rust package on Linux, glibc and musl, which CI's first run
   will do for glibc; the search for `native-static-libs` libraries is untested on a real
   system.

## Decisions made while building, for review

Joe did not make these; each is above with its reason.

- `isize` and `usize` cross as `int` and `ulong` (decision 4).
- The macro crate is two crates, and the runtime's library is named `jade` (decision 2).
- The generated crate is per project, not per program, with one shared target directory
  in `~/.jade/rust/` (decision 10).
- Every value crosses as a pointer (decision 5).
- macOS programs with a Rust package link against the SDK (decision 11).
- `abi` must be written, and prebuilt `abi = "jade"` libraries are removed with the C ones
  (decision 13 and *What is removed*).
- Rust dependencies are pinned by cargo, not by `jade.lock` (decision 13).
- Text from a Rust package stays tainted (decision 6).
- A panic's message names the function: `<package>.<function> panicked: ...` (decision 9).
- A borrowed result, such as `-> &str`, is accepted and copied, rather than refused
  (decision 3).
- A Jade literal of a Rust struct's class gives every field, since Rust gives none a
  default (decision 9).
- Handles and callbacks, which the C path had, are dropped for now rather than carried
  over, since neither has a Rust shape yet that the rest of this design settles; both are
  follow-ups (*Out of scope*).
- `jade check` builds the Rust, and `jade pkg add` builds a Rust package to report what
  it exports (decisions 7 and 13).
